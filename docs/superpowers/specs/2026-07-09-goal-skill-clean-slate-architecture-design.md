# /goal 生文 Skill 从零架构设计（planner/writer/verifier 三件套）

> 日期：2026-07-09 · 性质：概念性目标架构（clean-slate 思路推演），不是对现有三份
> `geo-goal-orchestrator` / `geo-article-writer` / `geo-article-verifier` SKILL.md 的逐行 diff。
> 本文档刻意不参照现有 skill 实现写成，也不与同日已存在的
> `2026-07-09-goal-loop-speedup-design.md`（配图延后 + 去重复查询的精确 patch 方案）互相对齐或引用——
> 两者是独立产物，按用户要求各自成文。

## 背景

`/goal` 生文变慢的表面诉求是"能不能加 Redis 缓存模板/问题读取"。追下去发现：模板和问题的 DB
查询本身是毫秒级索引查询，真正的浪费在于**多代理协作的结构**——orchestrator（下称 planner）
早已查到的数据，fresh-context 的 writer / verifier 子代理又各自重新问了一遍 MCP。Redis 缓存服务端
查询延迟对这类"重复发起跨进程调用"本身没有帮助（省不掉那趟往返，只能让往返里几毫秒的 DB 部分
更快，而往返开销主要不在 DB 那几毫秒上）。

于是把问题往前退一步：如果不修补现有实现，而是从零设计这套"planner 调度、fresh-context 子代理
干活"的 skill 架构，应该长什么样？本文档记录这次讨论收敛出的目标架构，供未来重写或新设计同类
MCP 多代理 skill 时参考。

## 架构总览

```
planner（主对话，长期持有 catalog 查询结果）
  ├── 选题/派发：list_question_pools / list_question_items / list_prompt_templates
  │              / list_today_loop_articles / notify_feishu
  ├── spawn → writer（fresh context，每篇/每次重写一次）
  │              工具：save_article / ai_illustrate_article / report_event
  │              入参：结构化 packet（question_text / template_content 等已解析好的数据）
  │              出参：结构化 JSON（article_id / title / 配图判断结果）
  └── spawn → verifier（fresh context，每轮一次）
                 工具：get_article / submit_review_decision / report_event
                 入参：结构化 packet（question_text / template_content + article_id）
                 出参：结构化 JSON（decision / score_total / weak_dims）
```

三个角色只有 planner 会持续存活、持续拥有"已经查过什么"的记忆；writer / verifier
每次 spawn 都是白纸，只认 planner 塞给它的东西。

## 决策 1：Skill 边界按 MCP 工具的读/写/评估三分类切

GEO 现有 26 个 MCP 工具天然分三组：catalog（12 个只读）/ action（10 个写）/ meta（4 个评估回流）。
这条分组线直接拿来当 skill 边界：

| Skill | 对应工具组 | 唯一职责 |
|---|---|---|
| 选题与派发（planner 自身） | catalog（部分） | 把自然语言目标变成结构化工作清单，不写文章、不评分 |
| 单篇写作 | action（部分） | 给定完整数据 packet，产出一篇文章 + 落库 + （视情况）配图 |
| 评审 | action（部分）+ get_article | 只读 `get_article`，只写 `submit_review_decision`，不碰 `review_status` |

不做"一个 skill 塞多个工作流"——三个独立触发条件，三份独立文档，避免 description 互相打架、
也避免一份文档过长压过 token 预算。

## 决策 2：数据契约是结构化 packet，不是"子代理自己想办法拿"

Planner 在选题阶段已经拿到候选问题（含 `question_text`）和模板列表（含 `content`）。
这份数据本身，从"要不要重新查一遍"这个角度看，对 writer / verifier 是**已知数据**：

```
writer 入参 packet:
  qid, question_text, tpl_id, template_name, template_content,
  model_label, rewrite_feedback (可为空)

verifier 入参 packet:
  article_id,                          # 唯一的"新数据"，其余字段 planner 已知
  qid, question_text, tpl_id, template_name, template_content
```

`article_id` 对应的文章正文是**真正的新数据**——planner 从没持有过，verifier 必须靠
`get_article` 去拿落库后的真实内容（草稿意图 ≠ 最终产物，尤其是配图会改变 content_json）。
这是唯一允许"子代理自己去查"的例外，其余一律由 planner 直接注入 prompt。

**为什么这条要在设计阶段就定死，而不是留一句"建议 planner 传、传了就用"的软提示**：
子代理在不确定时天然有"顺手再查一次保险"的倾向，这是执行纪律类问题，光靠文字劝说很难在
压力/不确定性下守住。

## 决策 3：用工具权限隔离，而不是 prompt 软约束，杜绝"重复查询"

比"prompt 里写清楚优先用 input"更彻底的做法：**subagent 的可用工具集里物理上不包含
它不该用的 catalog 查询工具**。Claude Code 的 subagent 类型支持按 `tools:` 白名单裁剪权限，
所以从零设计时不该把 writer / verifier 挂在通用的 `general-purpose`（继承全部工具）下，
而是各自定义专属类型：

| 子代理 | 保留的工具 | 明确排除 |
|---|---|---|
| writer | `save_article` / `ai_illustrate_article` / `report_event` | `list_question_items` / `list_prompt_templates`（不是"不让用"，是**拿不到**） |
| verifier | `get_article` / `submit_review_decision` / `report_event` | 同上两个查询工具 |

工具集里没有的调用，模型无论多"手贱"都发不出去——这比任何 prompt 措辞都可靠，且验证成本为零
（不需要跑压力场景去确认它会不会走捷径，因为捷径根本不存在）。

## 决策 4：区分"免费的进程内交接"和"有真实成本的 MCP 往返"

MCP 工具调用底层也是 JSON-RPC，所以真正的分界线不是"JSON vs MCP"，而是：

- **免费**：planner → subagent 的 `Agent()` prompt 参数、subagent → planner 的最终返回值。
  这两者都是同一次调用的请求体/响应体，不产生额外网络往返。所有"已知数据"的传递都该走这条路径。
- **有真实成本、且必要**：
  1. `save_article` / `submit_review_decision` 这类**落库即交付物**的写操作——这不是通信开销，
     是系统存在的意义，省不掉。
  2. 像"累计过审数"这种**故意设计成不信子代理自报、必须回库核验**的独立核验点——这是刻意的
     冗余换正确性，不是浪费，不应该被"提速"思路误伤。

提速该砍的是"子代理为了拿本该已知的数据而发起的查询"，不是这两类必要成本。

## 决策 5：失败重试分两条完全独立的机制

| 失败类型 | 触发条件 | 处理方式 |
|---|---|---|
| 基础设施类 | MCP 超时/网络抖动/认证错误 | 原样重放同一次调用，不改变任何输入，有限次数（如 2~3 次）+ 退避。连续达到阈值（如 3 次）→ 判定 MCP 整体不可用，**整体熔断退出**，不再对每个工作项各自撞墙 |
| 内容质量类 | 评审打回（`needs_rewrite`/`rejected`） | **不是重试同一动作，是带着失败原因重新生成**——必须把 `weak_dims` + `reasoning` 喂给下一次写作。独立预算上限（每题最多 N 次重写），防止死磕一道题耗光资源 |

**是否值得在同一题上死磕**是策略选择，取决于这道题是否被用户"钦点"（精确点名）：
钦点的题值得多花预算重写；自动挑选、非钦点的题失败了直接换下一题更划算——目标是凑够总产出数，
不是逐题攻坚。

**幂等性是这条设计最容易被忽视的风险点**：如果落库调用超时、但服务端其实已经写成功，
基础设施类的"无脑重试"如果没有幂等保护会产生重复文章。这条在实现前必须先确认写接口
是否天然幂等（有无 idempotency key），没有的话"无脑重试"这个策略本身需要先补上这一环。

## 决策 6：打点是给"人不在场也能看懂发生了什么"，不是调试日志

- 按**状态转换**打点，不是按起止打点——多阶段流水线（选题→写作→配图→评审→决策）每个阶段的
  进入和结果都该有对应事件，让中途查看日志的人能知道卡在哪一步。
- **一件事只由一个角色打点**：避免 planner 和子代理对同一信息重复打点造成噪音。
- 失败事件必须带够归因信息：基础设施类还是内容质量类、第几次尝试、具体原因——不能只写
  "失败了"。
- **"什么都没发生"本身也是该记录的事实**（如 AI 判断不需要插图、某题重写预算耗尽仍未通过）——
  这类分支最容易被漏记，因为表面上"没出错"，但恰恰是运营最需要知道的信息。
- payload 用结构化字段（id、枚举），不是一句话——后续要按字段做统计分析。

## 决策 7：配图不是关键路径，插入方式取决于正文结构

- **插在哪**：取决于正文有没有清晰锚点。每个实体各占一个小标题的结构 → 可以做确定性锚定
  （逐个收集实体名对应插图，不依赖模型猜）；没有分标题的综述/散文 → 没有锚点可用，只能退回
  让模型读全文自己判断。这个判断只有写作者自己知道（生成的文本是否有锚点），所以该在写作阶段
  产出正文的同时顺手做出，不该等到配图步骤才现场分析。
- **凭什么插**：图库分类（主推栏目）该是跟着内容矩阵/题材走的配置项，从上游配置传下来，
  不是写作者临时决定——这也属于"已知数据不该临时现查"的同一类原则。
- **是否关键路径**：不是。插图失败或插了 0 张不该导致重写或判定整体失败——文字本身已经是
  完整交付物；但这个结果必须被打点记录，不能悄悄吞掉。

## 决策 8：文章落库时机——写完立刻落库，评审是落库后的独立标注

- **落库应该在写作一结束、拿到成文文本后立刻发生**，不等配图、不等评审。
- 理由一（结构性）：配图操作需要在一个已存在的 article 上进行（拿 `article_id` 做参数），
  落库必然先于配图，这是工具调用链本身决定的顺序。
- 理由二（容错性）：越早落库，容错性越好——下游配图/评审任一步骤崩溃，文字稿已是持久化产物，
  不会因为非关键步骤失败而让整篇工作白费。
- 理由三（安全边界）：评审不该是"能不能落库"的门槛，而应该是落库之后的独立标注动作——
  评审产出一条"决策记录"，不直接改文章的可见状态，最终能否发布仍由人工终审兜底。
  即使自动评审误判（比如错杀一篇其实不错的稿子），文章本体仍在库里，人工可随时复核，
  不会因一次自动判断彻底丢失内容。这也是"自动评审只做筛选/计数信号，不做硬闸门"的
  设计动机所在。
