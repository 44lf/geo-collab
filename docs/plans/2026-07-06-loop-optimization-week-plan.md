## 一、飞书在线审核（详细设计 · 定稿）

### 1.1 场景与群拓扑

- 审核发生在 **群 2（GEO 发布群，已投产）**。该群当前只有一个 webhook 机器人。
- 群 1（正式 GEO 群）里有一个**自建应用机器人**（只读多维表用），凭据 `GEO_FEISHU_APP_ID` / `GEO_FEISHU_APP_SECRET` 已在 env。

### 1.2 方案选型结论

- **弃**：webhook 跳转型审批按钮（点了只能跳浏览器，做不到"飞书内直接通过"）。
- **弃**：「不通过」按钮（拒稿在 web 端做）。
- **采用**：**复用群 1 的自建应用**（不新注册），扩机器人+回调能力、拉进群 2，发**交互卡片**，卡片上并存**三个元素**：
  - **「通过」= 回调按钮** → 飞书内点击**直接** `approved`，卡片原地更新为"已由 XX 通过"、按钮置灰，**不跳转**。
  - **「看全文」= `open_url`** → 飞书 webview 内打开**免登录签名只读预览页**，看全文+图（**不把全文灌进群聊**）。
  - **「打开修改」= `open_url`** → 点进 web 登录编辑页，对该文章微调正文再批 / 拒稿。

> 因为要真回调，这张审核卡片必须由**应用机器人**发（`im/v1/messages`），不能走 webhook 发（webhook 卡片按钮只能跳转、点了不回调）。原 webhook 保留发其它单向通知（loop 完成、失败告警）。

### 1.3 要做的组件

1. **两张文章页（承重件）**——对应卡片的「看全文」和「打开修改」，用途不同、都要做：
   - **1a 签名只读预览页（免登录）**：后端渲染 `content_html`+图片，HMAC 签名+时效校验；供飞书「看全文」webview 打开。看全文+图，不能编辑。
   - **1b 登录深链编辑页**：前端新增路由 `/content/article/:id`（当前 `web/src/routes.tsx` 只有列表、无单篇深链），复用现有编辑器；登录后可读、可微调、可批（复用现有 approve + 审计）。
2. **自建应用扩能力 + 进群 2 + 拿 `chat_id`**（纯配置活）
   - 开启机器人能力、订阅"卡片回传交互回调"、配 `encrypt_key` + `verification_token`、申请 `im:message` 发送 scope、把应用拉进群 2、记录群 2 `chat_id`。
3. **回调端点** `POST /api/feishu/card-callback`（新增，最易踩坑）
   - challenge 握手 → AES 解密 → 验签 → flip 状态 → **3 秒内**返回更新后的卡片。
   - 非 MCP-token / 非 JWT 路径：靠 `encrypt_key` + `verification_token` + 签名校验（飞书回调带不了 X-MCP-Token）。
4. **发卡片（应用机器人）**
   - `tenant_access_token` 刷新逻辑现成（`shared/feishu_bitable.py`）；拼卡片 2.0 JSON，按钮 `value` 带 `{article_id, action:"approve"}`，调 `im/v1/messages` 发到群 2。

### 1.4 关键约束 / 验收标准

- **3 秒响应**：approve 是一次快 DB 写，稳在 3 秒内；如需重活走异步。
- **幂等 + 懒同步（重点）**：点「通过」前先查 `review_status`；已 `approved` 则**只返回当前状态 + toast「已通过」，绝不重复执行、不报错**。回调顺手把该卡片刷成真实状态（懒同步）。
- **状态守卫**：flip 用 `pending → approved` 条件 UPDATE + rowcount 判断，扛住"web 与飞书几乎同时点"的并发（第一个成功，第二个收到"已通过"）。
- **单一真值**：飞书与 web 写的是同一个 `review_status`，web 端读 DB 永远最新；唯一会"过期"的是已发出的飞书卡片（由懒同步兜底）。
- **审计**：回调事件带点击人 `open_id`，approve 时记进审计（现有 approve 本就写审计日志）。

### 1.5 本次不做 / 暂缓

- **「不通过」按钮**：不做，拒稿走 web 端。
- **主动推卡片更新（档位 B）**：web 端 approve 时主动更新那张飞书卡 → "已通过"。需存 `message_id` + 钩 web 审核路径 + 受**卡片更新时限/次数限制**（隔太久更新不了）。留待产品明确要求，约 +0.5 天 + 一个 `message_id` 存储。
- **权限门 / @指派审核 / 真实审计身份**：均依赖 **飞书 open_id ↔ GEO 用户（乃至 loop/MCP 身份）映射**，属"三端账号打通"前置轨道，见 §1.8。本周不做。

### 1.6 卡片三元素（已确认，全部要做，非三选一）

审核卡片上并存三个元素，各司其职：

1. **「通过」按钮（回调）** —— 飞书内点击→该文章 `approved`（按 article_id 单独操作）。**per-article approve 接口现已存在**（`articles/router.py` approve，user JWT），新增的只是"飞书回调按 id 调它（无 JWT、走签名校验）"这条入口，**不是从零做单抓单篇**。
2. **「看全文」（签名只读预览）** —— `open_url` 打开免登录 HMAC 签名+时效的只读 H5 页，飞书 webview 内看全文+图，**不把全文灌进群聊**。
3. **「打开修改」（登录深链编辑页）** —— 链接点进 web，登录后对该文章微调正文再批（复用现有编辑器 + approve）。

> 关系：2 给"读了就快批"（配 1）、3 给"要改稿"。2 与 3 是两张不同页面（免登录只读 / 登录可编辑），都要做。

**唯一剩的取舍**：若想省 ~1 天，可砍掉 2，让"看全文"也走 3 的登录页——但那样在飞书内瞄一眼全文就得先登录，失去"免登录速览"。默认保留 2。

**审计/指派身份**：本周只记原始飞书 `open_id`+姓名；真实身份映射 / @指派归 §1.8，本周不做。

### 1.7 在飞书内审核的边界（Q：能否不进 web 端）

| 模式 | 能看全文+图 | 能编辑 | 代价/限制 |
|---|---|---|---|
| 纯卡片渲染 | 仅短文/预览 | ❌ | 图须先下载→上传飞书换 img_key→嵌入；卡片有元素/长度上限，长文富文本渲染差 |
| `open_url` → 飞书内置 webview 打开深链页 | ✅ | 需登录态 | 底层仍是 web 页，只是在飞书容器内渲染（体感"没离开飞书"） |
| **签名只读 H5 预览页（推荐补充）** | ✅ | ❌（只读） | 免登录、HMAC 签名+时效；渲染 `content_html`+图片；配「通过」回调=读+批全程在飞书 |

**结论**：「在飞书内看全文+图」可行（webview / 签名只读预览）；但**「在正文里微调」是硬边界，必须回 web**——飞书卡片编辑不了富文本。所谓"在线弹窗"最终仍是一张 H5 页在飞书容器里渲染，不是脱离 web 的独立能力。

### 1.8 身份 / @指派审核 → 依赖三端账号打通（前置轨道，另立项）

- **@某人来审** 与 **真实审计"谁批的"** 是同一个依赖：都需 **飞书 open_id ↔ GEO 用户** 身份映射（若还要 loop 侧发起人可追溯，再加 loop/MCP 身份）。
- 这构成一条**前置基础轨道：loop · GEO · 飞书 三端账号打通 / 账号管理**，体量大于本周任一条线，**单独立项**，不塞进本周。
- 落地后解锁：卡片 @指定审核人、按人指派、真实审计身份、权限门（谁能点通过）。
- **本周 MVP 降级**：不做映射；回调 approve 只记原始飞书 `open_id`+姓名（或"经飞书通过"）入审计。@审核 / 真实身份 / 权限门等账号打通落地后再接。

## 二、重试 & 失败后通知（要点）

- 生文失败**自动重试**（限次数），落在 loop / `scheme_executor` 路径。
- 重试仍失败 → **飞书告警**（复用 webhook），带问题/模板/错误摘要。
- 幂等：重试记录不得再计入"已生成"。

## 三、增加日志（要点）

- 生文/loop 关键节点结构化日志（开始 / 成功 / 失败 / 重试各一条）。
- 落库可查或 UI 可见，可参考 pipeline 现成的 `node_results → 运行日志`（`run_logs.py`）那套。
